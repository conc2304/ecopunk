## 7. Previous/next behavior

Implemented exactly per §4.2/§9 and the Semantic Slot Review's "Proposed navigation semantics": Previous replays the immediately preceding successfully-activated item from session history; Next replays a forward history entry if one exists (the user previously went back), otherwise picks a fresh eligible item and discards any stale "redo" entries. Both reset the hold clock only on confirmed success, mark `selectionOrigin` correctly, and reject cleanly (return `false`, no state change) when unavailable — including the one-item-catalog case, where both directions are `false` as specified. Fully covered by `video_selection_policy_tests.cpp` (`test_manual_previous_replays_prior_history_entry`, `test_backward_then_forward_history_traversal`, `test_fresh_forward_step_after_going_back_clears_stale_redo`, `test_one_item_catalog_navigation_disabled`).

`blob-region-prototype` does not call `next()`/`previous()` anywhere — it never had a next/prev command before migration (confirmed in `docs/video-playback-ownership-probe-report.md`'s per-scene matrix), and adding one was out of this migration's scope (§9 Stage 2 asks to preserve existing behavior, not add new UI). No scene or harness currently invokes `next()`/`previous()` in a real build — see "Deviations from this prompt."

## 8. Hold and progress behavior

Hold timer: starts at `0` on `confirmActivationSucceeded()` (which only ever fires after a *confirmed* successful decoder load — never on load start), advances only while `health == Ready`, resets on every successful activation regardless of origin, clamps `holdProgress` to `[0,1]`, `holdRemainingSeconds` never negative, all four hold fields `nullopt` together when `automaticAdvance == false`. Unit-tested exhaustively (`test_hold_starts_at_zero_after_confirm`, `test_hold_progress_and_completion`, `test_hold_progress_clamps_and_remaining_never_negative`, `test_manual_navigation_resets_hold`, `test_automatic_advance_resets_hold_for_new_item`, `test_disabled_automatic_advance_yields_absent_hold_fields`).

Playback progress: loop-relative (`ofVideoPlayer::getPosition()`, `[0,1]`), `nullopt` (not `0`) whenever `duration <= 0` or `position < 0` (decoder reports "unavailable"). This half is decoder-facing and validated by the real build, not the pure test suite — see §14.5's own instruction to split these.

`blob-region-prototype` sets `automaticAdvance = false` explicitly, preserving its pre-migration "play the same clip forever" behavior — this is a deliberate, documented choice (see the code comment at the `VideoPlaybackService::Config` construction site in `ofApp.cpp`), not an oversight; enabling automatic advance for this scene would have been a real behavior change the migration prompt's own "preserve existing visual output" instruction forbids.

## 9. Error and recovery behavior

Missing media root → catalog stays empty → `Unavailable` + `messageId`, no crash (`setup()` still returns `true`). Empty catalog (root exists, zero files) → same. Duplicate `mediaId` → later entry rejected, logged, first kept. Missing/malformed catalog JSON file → logged, ignored, auto-synthesis proceeds unaffected. Failed decoder load → `attemptSelection()` retries via `policy_.requestRecoveryCandidate()`, bounded by the playable-item count (never an infinite loop), final successful activation reported with `MediaSelectionOrigin::Recovery` if any prior attempt in that call failed; if every candidate fails, `health = Failed` with a `messageId`. No raw backend exception text is ever placed in `messageId`/`errorCode` — both are stable string constants (`"media.error.*"`), matching §12's "do not display raw backend exception text" instruction.

## 16. Newly discovered risks

1. **`PROJECT_EXTERNAL_SOURCE_PATHS` with more than one space-separated value silently mis-builds object paths the moment any of those paths contains real (non-header-only) source files.** Confirmed by direct build failure (`No rule to make target obj/osx/Release/..shared/src/video-playback/VideoPlaybackService.o`) when `experience_runtime/config.make` initially listed three space-separated external paths. Root cause: `config.project.mk:568`'s `OBJS_WITHOUT_EXTERNAL = $(subst $(strip $(PROJECT_EXTERNAL_SOURCE_PATHS)),,$(OBJS_WITH_PREFIX))` treats the entire multi-word variable as one literal search string, which never matches any individual object's actual path. This had gone unnoticed in this specific sketch because its previous two external paths (`shared/src/scene`, `shared/src/hud-runtime`) were both header-only, so no object was ever generated from them to expose the bug. **Fixed** by scoping `experience_runtime`'s `PROJECT_EXTERNAL_SOURCE_PATHS` to exactly one value and adding the two header-only directories via `PROJECT_CFLAGS -I` instead. This is a pre-existing Makefile-system limitation (already partially documented in `quadrant-crosshair/config.make`'s own comments, now empirically confirmed rather than just warned-about) that will resurface for any future sketch/increment that tries to list more than one external source path containing real `.cpp` files.
2. **Multiple `main()`-defining standalone test files already exist directly inside `shared/src`'s tree** (`shared/src/video-effects/test/effect_knowledge_extension_tests.cpp`, `shared/src/hud-compositor-test/{debug_issues,hud_presentation_tests}.cpp` — the latter is a top-level directory, not nested under a `test/` folder, so a `%test%`-style glob wouldn't have caught it) and **collide at link time** with any sketch that uses an unscoped `PROJECT_EXTERNAL_SOURCE_PATHS = ../../shared/src` with no exclusions — confirmed directly: `blob-region-prototype` failed to build with `duplicate symbol '_main'` pulling in exactly these files, **before this increment's own `shared/src/video-playback/test/` was even considered**. This means `blob-region-prototype` (and likely every other sketch using the same unscoped, no-exclusion pattern — `blueprint_emergence`, `temporal-fields`, `contour-portrait` all currently do, per their own `config.make` files) has been in a **build-broken state** since whichever of those test directories landed most recently, independent of this increment. **Partially fixed**: `blob-region-prototype/config.make` now excludes all three known offending directories (its own newly-added dependency, `video-playback/test`, plus the two pre-existing ones) so this increment's own target scene builds — but the other affected sketches (`blueprint_emergence`, `temporal-fields`, `contour-portrait`) were not touched and are very likely still broken. This should be escalated to whichever domain owns `shared/src/video-effects/` and `shared/src/hud-compositor-test/`, or to Architecture as a repo-wide Makefile-hygiene issue, since it isn't scoped to any one subsystem.
3. **`experience_runtime`'s own `RuntimeServices::setup()` is a silent no-op when `Config::mediaRoot` is empty.** This is intentional (see the code comment), but it means a future caller that forgets to configure the video service gets no error signal at all, just a permanently-`nullopt` `HudFrameData::video` — worth a louder failure mode (an assert or log) if this pattern is kept once real scenes depend on it.

# HUD Layout Integration & Raspberry Pi 3B+ Feasibility Probe

**Purpose**: a read-only architectural probe answering one question — what is the lowest-cost, lowest-risk way to build the proposed upper-left media viewport + L-shaped HUD panel layout (rounded corners, 45° bottom-right bevel, contextual labels/status/controls) on top of this monorepo, while preserving Pi 3B+ feasibility? No code was written or modified to produce this report.

**Method**: built on top of the existing `docs/scene-consolidation-probe.md` (818 lines, dated 2026-08-01, covering per-sketch `setup()`/`update()`/`draw()` order, FBO ownership, build status, and shared-infrastructure usage for all 11 sketches — treated here as established fact, not re-derived) plus direct reading of `shared/src/hud/`, `shared/src/hud_overlay/`, `shared/src/video-effects/core/`, `shared/src/ErosionFBO.h`, `sketches/temporal-fields/src/TFFragmentShape.h`/`TFShapeFragmentRenderer.cpp`, and two focused research passes: (1) per-sketch HUD status-data accessors and command surfaces, read directly from each `ofApp.h`/`.cpp`; (2) existing performance instrumentation, Pi hardware-telemetry usage, and build/deploy blockers, including a check of the sibling `apps/myApps/FireplaceWaterfall` app's Pi deployment scaffolding as potential reusable prior art. All findings below are grounded in specific file paths and symbols; inferences are labeled as such.

---

## 1. Executive Finding

**Yes, architecturally feasible — but not for free, and not uniformly across sketches.** The repo already contains three independent, proven precedents for exactly the pieces this layout needs:

1. A **caller-owned render-target contract** already exists and is actively honored, just one layer too low: `VideoEffectContext::destinationFbo` (`shared/src/video-effects/core/VideoEffectContext.h:34`) is an optional FBO — "null = draw to whatever's currently bound" — and all 7 effect implementations in `shared/src/video-effects/effects/` correctly bracket their own internal FBO work around it. No sketch's whole `ofApp::draw()` has this contract yet; extending it one level up (scene → HUD compositor) is a small, well-precedented step, not a novel design.
2. A **shader-free, Pi-safe polygon-mesh clip** already exists in production code: `sketches/temporal-fields/src/TFShapeFragmentRenderer.cpp`'s `buildWedgeMesh()` clips live video content to an arbitrary non-rectangular silhouette (a pie-slice/ring wedge) using a hand-built `ofMesh` with manually-computed normalized texcoords (required because `ofDisableArbTex()` is load-bearing repo-wide). The same technique — vertices tracing the rounded-corner + 45° bevel outline instead of an arc — is the cheapest, most Pi-consistent way to build the proposed viewport shape, and it can draw a matching border in the same pass.
3. A **vector-only, arbitrary-bounds HUD widget library** (`shared/src/hud/`, 19 widgets + `WindowChrome`) is already Pi-oriented by design (no shaders/FBOs/textures, text via `ofDrawBitmapString` not `ofTrueTypeFont` so zero glyph-texture cost) and every widget accepts `setBounds(x,y,w,h)` — placing widgets inside the L-panel's two rectangles requires zero new widget code.

**What remains unproven until Pi testing**: everything numeric. No sketch in this repo has ever been profiled on real Raspberry Pi 3B hardware (confirmed again directly: zero `vcgencmd`, zero thermal/throttle/GPU-memory telemetry anywhere in the tree). `shared/src/hud/README.md` itself states Pi FPS validation is "currently outstanding," and that claim is *not* backed by any measurement code anywhere in the repo — not even a desktop per-widget draw-cost number exists. Separately, a real and previously-undocumented architectural risk surfaced in this probe (see §5): naively wrapping a sketch's whole `draw()` inside an *outer* caller-owned FBO is not free for the ~6 of 9 sketches that already own internal ping-pong FBOs (`ErosionFBO`, `RPRevealMask`, `Quadrant`'s erosion pair, `TFComposition`'s transition-snapshot pair) — whether OF's view/matrix push-pop stack nests correctly under a second, outer `ofFbo::begin()/end()` has never been exercised in this codebase and must be verified empirically, not assumed.

**Most cost-effective integration direction**: build the HUD compositor as a **thin outer adapter wrapping exactly one sketch at a time**, prototyped first against `shader-effect-debugger` (the one sketch already built directly against the `destinationFbo` contract, with zero local forks). Do **not** wait for Scene/SceneManager consolidation to start this work, and do **not** attempt "next/prev sketch" switching inside the first PoC — that specific capability is genuinely blocked on the consolidation work's class-name-collision and process-ownership questions (§6). Everything else — the clip geometry, the widget layout, the status/command contracts' *shape*, and the instrumentation — can and should proceed now, one sketch at a time, using the same incremental-adoption pattern this repo already used successfully for `shared/src/video-effects/` and `shared/src/hud/`.

## 4. Missing Contracts

### Scene rendering/output contract
**Does not exist at the whole-`ofApp` level in any sketch.** The closest and best precedent is `VideoEffectContext::destinationFbo` (§3) — extend that exact shape (`ofFbo* target = nullptr; // null = draw to whatever's bound`) to a new scene-level call, rather than inventing a fresh `IScene` interface from a blank page. Concretely: `draw(const ofRectangle& viewport)` is **not** sufficient by itself for the ~6 sketches with internal FBOs (fixed constants like 1280×720 are baked into geometry math, not derived from the passed rect), so the safer near-term shape is an FBO-owning adapter that (a) allocates an offscreen FBO at the sketch's *native* assumed resolution (1280×720 for every sketch in this repo today), (b) calls the sketch's existing `draw()` unmodified inside that FBO, and (c) blits/mesh-draws the result into the HUD viewport rect — **provided** the nested-FBO-under-outer-FBO question (§2, hazard 1) is empirically cleared first per sketch.

### Read-only status/metadata contract
Data exists per sketch (full inventory gathered directly from source — see the companion per-sketch table produced during this probe), but reachability is inconsistent:
- **Universal, safe to poll everywhere**: `ofGetFrameRate()` (an OF global, not sketch state — confirmed callable from anywhere with no side effects, and already drawn by 8 of 9 sketches' own overlays; `shader-effect-debugger` is the one exception, with no on-screen fps at all today, though the global itself is still available).
- **Present via a real public getter in most sketches, but not all**: media filename (`RPVideoSampler::getCurrentFilename()`, `VideoSystem::getCurrentFilename()`, `TimeOffsetVideoBuffer::getCurrentMediaFilename()` — present in 6/9; `blueprint_emergence`'s `VideoSampler` has no public filename accessor at all; `contour-portrait` has no "current preset name" state stored anywhere).
- **Exists but is currently private, needing a small additive getter**: `blob-region-prototype`'s `RollingAverage` timers, `radar-pulse`'s `msVideoUpdate`/`msMaskStampAndDecay`/`msComposite`, almost the entirety of `shader-effect-debugger`'s state (effect id/index/kind, video filename, evolution phase — all private members surfaced only via on-screen text draws, not accessors).
- **One real polling hazard found**: `quadrant-crosshair`'s `VideoSystem::fileChanged()` **clears its own internal flag on read** — polling it from an outer HUD would race with `ofApp::update()`'s own consumption of the same flag and could cause either side to miss the event. This is a concrete example of why a status contract needs to be additive (new getters), not "just read the existing flag."

Recommended shape, kept intentionally minimal per the task's own instruction not to build one giant shared state object:
- **Universal fields** (every scene must provide): fps (free, always available), an opaque `std::vector<std::string> statusLines` the scene fills in with whatever it wants shown, with no schema the HUD needs to understand.
- **Optional typed metrics** (`std::optional<T>`, presence-flagged): media filename, active-item count (blob/fragment/pulse/track — semantically different per sketch, so surfaced as one generic "count" field, not several named ones), phase/progress `[0,1]`.
- **Sketch-specific rows stay opaque** — folded into `statusLines` above, never modeled as first-class HUD fields, exactly as the task requested.

### Command/capability contract
Cross-sketch survey (full detail in the companion command-inventory table) found only two near-universal capabilities across the 9 interactive sketches: fps polling (universal, free) and a debug/GUI-visibility toggle (present in 8/9 — the one gap, `shader-effect-debugger`, has no GUI-visibility key at all, a one-line addition, not an architectural gap). Every other category — next/prev media, next/prev mode/pattern/preset, pause/resume, restart/reseed, HUD-overlay toggle, fullscreen, quit — exists in at most 5 of 9 sketches, confirming the task's own instinct: **the HUD must discover and hide unsupported actions per sketch, not assume a fixed command set.**

A second, distinct finding: even where a command exists, it is not always externally reachable without synthesizing a keypress. Most sketches wire `keyPressed` straight to a public method on an owned, reachable object (e.g. `quadrant-crosshair`'s `n` → `video.nextFile()`, a one-line public call). But `shader-effect-debugger` routes nearly every command through **private** `ofApp` methods (`prevEffect()`, `switchToEffect()`, `togglePausePlay()`, etc. are all private, `ofApp.h:26-28`), and parts of `blob-region-prototype`/`radar-pulse` similarly wrap otherwise-public sub-objects behind private members. These need small, additive public wrapper methods — not a rewrite — before an external command dispatcher can call them directly.

One safety question this probe could **not** resolve from static reading and flags as needing verification, not inference: `quadrant-crosshair`'s expansion-sequence trigger (`e`/`E`, `F1`-`F4` → `ExpansionDirector::trigger()`/`triggerQuadrant()`) is called unconditionally from `keyPressed` with no visible guard at the call site against re-triggering while already mid-sequence; whether `ExpansionDirector` itself guards internally needs a direct read of `ExpansionDirector.cpp` (not reached in this pass) before this command is considered safe to expose to an external caller that might fire it faster than a human would.

### Resize/lifecycle contract
Wildly inconsistent: `temporal-fields` propagates `windowResized(w,h)` to 5 owned systems (the best in the repo); `blueprint_emergence`/`fragment-trail` forward only to `hudOverlay`; `blob-region-prototype`/`contour-portrait`/both radar sketches/`shader-effect-debugger` have no meaningful resize handling at all (`contour-portrait`'s is a documented no-op that happens to work anyway because `effect.draw()` is already bounds-parameterized). **This gap does not block the PoC** if the media viewport is a fixed size matching each sketch's native 1280×720 assumption (the FBO-owning-adapter approach in §4 above sidesteps resize entirely — the sketch always renders at its native resolution into an offscreen FBO, and only the *final composite blit* into the HUD viewport needs to handle a size difference). It only becomes a real blocker if the product later wants the media viewport itself to be resizable at runtime.

## 5. Viewport Clipping Decision

The proposed shape — rounded corners, one 45° bevel at the bottom-right — needs to be evaluated against what this codebase already does, not against generic OpenGL best practice.

| Option | Evidence in this repo | Verdict |
|---|---|---|
| **Rectangular scissor + cover geometry** | Two live precedents: `sketches/fragment-trail/src/FTFragment.cpp:55-104` and `sketches/quadrant-crosshair/src/Quadrant.cpp:188-233`, both `glEnable(GL_SCISSOR_TEST)`/`glScissor(...)`/`glDisable(...)` bracketing a texture draw. Cheap, zero-shader, already idiomatic here. **But `glScissor` is axis-aligned only** — it can crop the viewport's rectangular bulk, but cannot by itself produce a rounded corner or a 45° cut. | Use for the rectangular majority of the viewport if combined with another technique for the two non-rectangular features; **not sufficient alone**. |
| **Polygon mesh through the completed scene texture** | Direct, working precedent: `TFShapeFragmentRenderer::buildWedgeMesh()` (`sketches/temporal-fields/src/TFShapeFragmentRenderer.cpp:27-67`) — CPU-built `ofMesh` (triangle fan/strip), normalized UVs computed by hand (required because `ofDisableArbTex()` is called in every video-using sketch's `setup()`), `tex.bind()/mesh.draw()/tex.unbind()`. Same silhouette drawn every frame with zero extra FBO passes and zero new shaders. | **Recommended — cheapest Pi-safe option, with concrete in-repo prior art.** Rounded corners approximated as short polyline arcs (matching `TFShapeFragmentRenderer::arcSteps()`'s existing "one step per ~6°, clamped 2-64" pattern), the 45° bevel as a single straight vertex cut. A second, slightly-inset outline drawn with `ofNoFill()` in the *same* mesh pass produces the border/frame for free — satisfying the task's "can it also produce a border without another pass" question directly. |
| **Stencil-buffer clipping** | Zero precedent anywhere in the repo. Every `useStencil` reference found (`shared/src/MotionExtraction.cpp:10,33,69` and its `quadrant-crosshair` fork) is explicitly `= false` — i.e. the one place stencil is even mentioned, it's turned off. | New, unproven GL state on a codebase that has never exercised it; higher risk of interacting badly with the scissor/blend-mode toggling that already happens per-frame in several sketches. Not recommended. |
| **Alpha-mask FBO compositing** | Real precedent: `RPRevealMask` (`sketches/radar-pulse/src/RPRevealMask.h`) — a 3-FBO ping-pong system (`captureFbo`+`fboA`+`fboB`) with a custom decay-then-max shader. Its own header comment explicitly explains *why* this was **deliberately not generalized** into `shared/src/hud/`: "this risk (ping-pong FBO cost, blend-equation availability) shouldn't leak into shared/src/hud and silently affect sketches that never touch this feature." | The repo has already made and documented this exact judgment call once. A *static* panel shape doesn't need per-frame recomputation at all (unlike RPRevealMask's moving pulses), making a full ping-pong FBO system substantially over-engineered for this use case. Not recommended. |
| **Fragment-shader SDF/shape mask** | No precedent anywhere; would be genuinely new shader work. `shared/src/hud/README.md` states the library's whole design premise is "no shaders, FBOs, or textures... for Raspberry Pi friendliness," and every shader in the repo is pinned to `#version 120` with careful `#ifdef PLATFORM_PI` precision-qualifier guards — an SDF mask adds a full-screen pass and a new maintenance surface with no proven benefit over the mesh option. | Not recommended for Pi-safe mode. |

**Pi-safe mode recommendation**: polygon mesh clip (rounded corners as short arc segments, bevel as a vertex cut), directly modeled on `TFShapeFragmentRenderer::buildWedgeMesh()`. Rebuilt only at setup/resize, not every frame (the shape is static). Combine with scissor for the rectangular L-panel body if profiling shows the mesh alone isn't cheaper there — this is exactly the kind of relative-cost question the on-device validation plan (§8) exists to answer, not to assume.

**Desktop/high-quality mode**: this probe found no strong evidence for a *different* technique being worth the added complexity. Every hand-rolled arc/curve in this repo (`GaugeWidget`, `RadarStationWidget`, `TFShapeFragmentRenderer` itself) already uses the same polyline/mesh approach at both quality tiers — the repo has no precedent for a desktop-only shader path anywhere. **Recommendation**: reuse the identical mesh-clip path on desktop, optionally raising the arc-segment count (the existing `arcSteps()` pattern already clamps 2–64 based on angular span — the same clamp, just allowed to reach further, is a one-line difference) for visibly smoother corners where the extra ~10–20 vertices cost nothing on a desktop GPU. This is a judgment call, not a static-inspection-proven fact — flagged explicitly as one to revisit if the PoC's visual comparison (§10) shows the mesh-only approach reading as too faceted at desktop viewing distance.

## 6. Scene Consolidation Dependencies

**Can proceed now, independent of Scene/SceneManager work** (per `scene-consolidation-probe.md`'s own findings plus this probe's direct evidence):
- Building the mesh-clip viewport shape (§5) — entirely self-contained, no dependency on multi-sketch embedding.
- Building the HUD chrome/layout using `shared/src/hud/` as-is — the widget library already works standalone per sketch.
- Defining the *shape* of the status/command contracts (§4) — these can be defined against and adopted by **one sketch first**, the same low-risk incremental-adoption pattern this repo already used successfully for `shared/src/video-effects/` (migrated sketch-by-sketch, second-wave candidates explicitly deferred) and `shared/src/hud/` (consolidated from 3 drifted copies into 1, with a uniqueness-check script as a backstop).
- Lifting `RollingAverage`/the µs-bracket timing pattern into `shared/src/` (§3) — a small, self-contained extraction.
- Building the on-device validation harness (§8) — needs one wrapped sketch, not all of them.

**Must wait for, or explicitly stub around, Scene/SceneManager work**:
- Any HUD control that implies **switching between sketches live in one process** ("next/prev sketch"). `scene-consolidation-probe.md` already documents the concrete blockers: real class-name collisions across sketches (`ShaderLibrary`/`LFOBank`/`TriggerBus`/`GridState` each independently forked and colliding at the `shared/src` top level between `blueprint_emergence`, `quadrant-crosshair`, and `fragment-trail` — handled today only via fragile, order-sensitive `PROJECT_EXCLUSIONS` wildcard matching in each sketch's `config.make`), process-lifetime singletons in the video-effects service pattern (`Quadrant.cpp`'s lazily-initialized `VideoEffectRegistry`), and every sketch assuming exclusive ownership of the window/cursor/fullscreen/exit lifecycle (`quadrant-crosshair` calls `ofHideCursor()` and binds `ESC`→`ofExit()` unconditionally in its own `setup()`/`keyPressed()`). None of this blocks a single-sketch HUD PoC. It does block a HUD that lets a user cycle live between sketches without either (a) waiting for consolidation, or (b) building an interim shell that launches/embeds sketches as **separate OS processes** and switches via process restart or window-manager focus — an option the original task explicitly asked to be assessed and which remains open, but which was not built or tested in this probe.

**Recommendation**: the first HUD PoC should wrap exactly one already-clean scene (see §10) and treat "next/prev sketch" as a documented-but-disabled entry in the command/capability contract until Scene/SceneManager consolidation lands — consistent with §4's capability-discovery design, which already requires hiding unsupported commands per scene rather than assuming a fixed set.

## 7. Performance Risk Model

Existing render passes, by sketch, are fully enumerated in §2's matrix — no repeat here. What the HUD compositor adds on top, in the recommended architecture (§4/§10):

- **One outer FBO capture of the wrapped scene** (if the FBO-owning-adapter path is used) — an additional full-canvas copy per frame, on top of whatever the sketch's own internal FBOs already cost. This is the single biggest open cost question and is explicitly **not estimated here** — no sketch in this repo has ever measured its own FBO capture cost in isolation, so there is no basis to project a number, only to flag it as the first thing the validation plan (§8) must measure.
- **One mesh-draw call** for the clip/border (§5) — the closest existing analogue, `TFShapeFragmentRenderer`'s wedge mesh, is drawn every frame today inside `temporal-fields` at desktop framerates with no documented cost complaint in that sketch's own performance notes; this is inferential evidence of "cheap enough to not be the first thing to break," not a measured number.
- **N `hud::` widget draws** for chrome/labels/gauges — governed by the library's own stated Pi-friendliness guidance (moderate node/particle counts, avoid multiple full-screen glow passes at once, use `setBounds` to scope each widget) — again, this guidance is prose in `shared/src/hud/README.md`, not backed by any measurement anywhere in the repo, including the one sketch (`hud_validation_harness`) that instantiates every widget class but never times a single draw call.

**No fabricated benchmark numbers appear anywhere in this report.** Every FPS/timing figure that exists in the codebase today is either an explicitly-labeled desktop proxy (e.g. blob-region-prototype's own `docs/blob-region-architecture.md`: "~11ms (≈75-80fps, vsync-limited) on the macOS dev machine," immediately followed by that same doc's own caveat that Pi 3B's Cortex-A53 cores are "roughly an order of magnitude slower per-core... this must be profiled on actual Pi 3B+ hardware") or simply absent (contour-portrait, shader-effect-debugger have no FPS target or on-screen counter at all). This report adds nothing invented on top.

## 8. On-Device Validation Plan

**Instrumentation to add on day one** (reusing, not reinventing, what's already proven in this repo):
1. Lift `blob-region-prototype`'s `RollingAverage` struct (`ofApp.h:102-118`) + its µs-precision bracket-timer pattern into a new `shared/src/PerfInstrumentation.h` — confirmed via grep that no such shared helper exists today; this is a small, low-risk extraction of already-working code, not a new design.
2. Generalize `hud_validation_harness`'s fixed-`dt`-step (`kFixedDt = 1.0f/60.0f`) + deterministic `ofSaveScreen()` + before/after `ofGetStyle().blendingMode` leak-check mechanism (`ofApp.cpp`'s `captureCurrentScenario()`) to wrap a scene+HUD composite draw instead of one `hud::HudWidget` — requires genericizing `Scenario::build`'s return type (currently `unique_ptr<hud::HudWidget>`), a small adapter change, not a rewrite.
3. Add the one piece confirmed **completely absent** repo-wide: `vcgencmd get_throttled`/`vcgencmd get_mem gpu` polling on a slow (~1s) timer, logged in the *same* `ofLogNotice("PerfStats") key=value ...` line format `blob-region-prototype` already established — this is the first real Pi-hardware telemetry anywhere in the repo, deliberately shaped to match existing tooling/expectations rather than invent a new log format.

**Stages to time explicitly** (matching the task's required list, using the contract from §4): wrapped-scene `update()`; wrapped-scene `draw()` (inside vs. outside the outer `destinationFbo` begin/end, to isolate the capture-nesting cost from §5/§7); HUD widget `update()`; HUD widget `draw()`; viewport clip/mesh draw; total frame.

**Comparison matrix** (per the task's required scenario list, mapped onto real sketches already in this repo):
| Scenario | Sketch(es) to use | Why |
|---|---|---|
| HUD disabled baseline | any | Establishes the wrapped-but-bare-scene floor |
| Rectangular viewport, no clipping | any | Isolates the mesh-clip's own cost from the FBO-capture cost |
| Polygon/mesh clipping enabled | any | Per §5's recommendation |
| Static L-panel enabled | any | Chrome-only cost, no live text |
| Dynamic text/status enabled | any | Adds `LogScrollWidget`/`TelemetryReadoutWidget`-style per-frame text |
| Representative data-viz widgets enabled | any | `GaugeWidget`/`DataCardWidget`/`ScannerWidget` |
| One lightweight scene | `blob-region-prototype` — only sketch with no `ofSetFrameRate()` call (vsync-limited only) and the one existing measured-cheap desktop number in the repo (§7) | Best available "floor" reference |
| One shader-heavy scene | `quadrant-crosshair` or `radar-effects-gallery` — most shader/FBO passes per frame of the 9 | Stress-tests GPU-bound cost |
| One FBO-heavy scene | `blueprint_emergence` (ErosionFBO) or `radar-pulse` (3-FBO reveal mask) | Directly tests the nested-FBO-under-outer-FBO hazard from §2/§5 |
| One CPU-heavy/blob-detection scene | `blob-region-prototype` again (own detector/tracker/region-update timing already instrumented) or `contour-portrait` (documented per-frame CPU readback, a deliberate Pi-driven design choice per its own `README.md`) | Both already carry the strongest existing CPU-cost documentation in the repo |

**Resolutions**: final output 1280×720 (matches every sketch's existing assumption); internal media viewport at whatever the design ultimately specifies as the panel's native size (a product decision, not determined here — see §11); a reduced internal render option (960×540 or 640×360, scaled up) has **direct in-repo precedent**: `contour-portrait`'s `ContourDisplacementEffect` already renders its GPU preprocess pass at 192×108/96×54/64×36 depending on quality preset, explicitly because "the real deploy target (Pi 3B/VideoCore IV/GLES2) does not reliably support sampling textures from a vertex shader" — the same reduced-internal-resolution technique this task's own investigation area suggested is already a proven, documented pattern here.

**Pass/fail criteria**: every current number in this codebase is explicitly unvalidated on real Pi hardware, and this report adds no invented threshold. A placeholder floor worth proposing for product sign-off — e.g. "sustained ≥20fps at 1280×720 with HUD, clip, and 2 representative widgets active, on the lightest scene, is the go/no-go floor for proceeding past PoC" — is flagged explicitly **as a placeholder requiring product confirmation**, not a derived fact.

**Logging format**: reuse `blob-region-prototype`'s exact `ofLogNotice("PerfStats") << "fps=..." << "detectorMs=..." ...` line shape — already proven stdout-capturable on a headless run (per that sketch's own comment, written with exactly this Pi-validation use case in mind) — so results diff the same way `hud_validation_harness` already diffs screenshots.

## 10. Recommended Proof of Concept

**Host**: `shader-effect-debugger`.

**Why**: it is the cleanest build in the repo (zero warnings), has **zero local forks** of any `shared/src` class (no name-collision risk relevant to future SceneManager work), and — critically — is the *only* sketch already built directly against the `destinationFbo` contract (§3/§4), which is exactly the seam the HUD compositor needs at the whole-scene level. Extending that exact, already-working pattern one layer up is a small, well-precedented step rather than a novel design, directly matching this report's "adapters over rewrites" mandate.

**Known downsides to budget for, not hide**: this sketch has no `ofSetFrameRate()`, no `PLATFORM_PI` conditionals anywhere, and — per §4 — the *weakest* external command surface of the 9 sketches (`prevEffect()`/`nextEffect()`/`togglePausePlay()` etc. are all private). The PoC needs a handful of small, additive public wrapper methods on its `ofApp` (not a rewrite) to reach next/prev-effect and pause/resume, which is exactly the kind of thin adapter work §4's command contract already calls for.

**What existing scene output it should wrap**: `currentInstance->render(context)`, redirected via `context.destinationFbo` — zero changes needed to any effect class; `ofApp::draw()` only needs to allocate that FBO at the panel's native resolution and pass it instead of leaving the field `nullptr`. Running the PoC's validation matrix (§8) against both a `SinglePassShaderEffect` (lightweight) and `ErosionEffect`/`TemporalTrailsEffect` (FBO-heavy, and the one place in the whole repo that already proves the nested-FBO-under-`destinationFbo` question works *at the effect layer*) gets both the "lightweight" and "FBO-heavy" comparison-matrix scenarios from **one** host sketch, via its existing arrow-key effect cycling — an efficient way to avoid wrapping two different sketches in the first pass.

**Viewport dimensions and L-panel geometry**: deliberately **not specified here** — this is a product/design decision this probe should not invent (see §11, open question #1).

**Selected clipping method**: the mesh-based polygon clip from §5, structurally templated directly on `TFShapeFragmentRenderer::buildWedgeMesh()` — built once at setup/resize (the shape is static), not per frame.

**Initial HUD widgets/text fields** (all directly instantiable from `shared/src/hud/` today, zero new widget code): `hud::WindowChrome` for the panel's border/label chrome — extended with a new `FrameStyle` value (e.g. `BeveledPanel`) inside `HudFrameRenderer`'s existing `switch` (§5's mesh technique, not a fork of `WindowChrome` itself); `hud::DataCardWidget` for effect name/kind; `hud::StatusLightWidget` for media-ready state; `hud::TelemetryReadoutWidget` or `hud::LogScrollWidget` for fps/frame-time readout; `hud::GaugeWidget` for one live numeric (e.g. evolution/drift progress, both already exposed as `ofParameter<bool>`s in this sketch).

**Minimum command set**: prev/next effect (`←`/`→`, exists today, needs a public wrapper), pause/resume (`space`, exists today, needs a public wrapper), toggle GUI visibility (does **not** exist in this sketch today — confirmed gap, needs adding), fps display (already free/universal). Deliberately **excludes** next/prev-sketch (blocked on SceneManager, §6) and restart/reseed (this sketch has no such concept at all) — consistent with per-sketch capability discovery rather than a fixed command set.

**Instrumentation from day one**: the lifted `RollingAverage`/timer pattern (§8), timing scene `update()`, scene `render()` (inside vs. outside the `destinationFbo` begin/end — directly isolating the §5/§7 nested-capture cost question), mesh-clip draw, HUD widget update, HUD widget draw, total frame — plus the periodic `PerfStats` log line in `blob-region-prototype`'s exact format for continuity with the one proven headless-capturable pattern in this repo.

**Effects/layers disabled for baseline**: no evolution, no drift; a single `SinglePassShaderEffect` (e.g. `desaturate`) for the lightweight baseline run; `ErosionEffect` or `TemporalTrailsEffect` selected for the FBO-heavy comparison run (same sketch, different effect selection).

**Comparing wrapped vs. original output**: visually, by reusing `hud_validation_harness`'s exact `ofSaveScreen()` + fixed-`dt`-step mechanism (§3/§8) to capture the *same* effect at matching logical time both unwrapped (today's direct-to-window path) and wrapped (through the new `destinationFbo` + mesh-clip path), then diffing the two PNGs pixel-for-pixel inside the media-viewport region (expected near-identical modulo the intended clip shape); numerically, by comparing the new `PerfStats` timing fields between the wrapped and unwrapped runs, on desktop first and on Pi once the build path from §9 exists.

**What result justifies proceeding to the full engineering handoff**:
1. Wrapped visual output matches unwrapped modulo the intended clip shape, with no GL state leakage (blend mode, scissor, viewport) — verified via the same before/after check `hud_validation_harness` already performs, not merely asserted.
2. The OF view/matrix push-pop nesting question (§2/§5, hazard 1) is **empirically confirmed safe** for at least the `ErosionEffect`/`TemporalTrailsEffect` case, not just inferred from the fact that `destinationFbo` is honored at the effect layer.
3. Desktop overhead of HUD + clip + widgets is small *relative to* the wrapped scene's own cost (a relative threshold, since only relative desktop numbers are trustworthy pre-Pi per §7/§8).
4. The harness successfully builds and boots on **real Raspberry Pi 3B+** hardware via the adapted `FireplaceWaterfall` deploy pattern (§9), and clears whatever fps floor product sign-off sets (§8's placeholder, not invented here).

**Structure the PoC as a reusable harness, not a demo**: build its `ofApp` as a thin wrapper analogous to `hud_validation_harness` (scenario list → fixed-dt-step → capture/measure → advance) rather than one-off code, so the same binary becomes this repo's first genuine Scene+HUD validation harness — directly extensible to additional sketches once Scene/SceneManager consolidation provides more wrappable scenes, per §6.

## 11. Engineering Handoff Readiness Checklist

**Enough is known to write an implementation handoff for**: the mesh-clip viewport technique (concrete precedent, concrete algorithm outline); the scene-rendering contract's shape (concrete precedent to extend, `destinationFbo`); which single sketch to prototype against and why; what instrumentation to add and in what format; and which parts of this work are blocked on Scene/SceneManager consolidation versus independent of it.

**Not yet known — requires a product/user decision, not further code inspection**:
1. **Exact geometry of the L-panel and viewport** — corner radius, bevel run length, panel thickness. A design decision; static inspection cannot supply it.
2. **The Pi fps/frame-time floor that constitutes "pass."** Every number in this codebase today is an explicitly-unvalidated proxy (§7). Product must set an acceptable minimum before §8's pass/fail line is real rather than a placeholder.
3. **Whether Pi-safe and desktop modes should use different clipping quality**, or one shared implementation is acceptable (§5's recommendation is a judgment call, not a requirement — worth revisiting after the PoC's own visual comparison).
4. **Whether "next/prev sketch" is required for the first shippable HUD**, or genuinely deferrable until Scene/SceneManager consolidation (§6). This single decision determines whether the PoC needs a process-embedding shell now or can defer that entirely.
5. **Whether physical control input (buttons/knobs) is in scope for this work**, versus keyboard-equivalent commands only. Confirmed entirely absent from every sketch today (§9) — a genuinely new capability if wanted, not an integration question.
6. **Raspberry Pi OS Lite (X11) vs. a Wayland-based deployment path.** Determines how much of `FireplaceWaterfall`'s deploy templates are directly reusable versus need reworking (§3/§9), and is itself a real open question blocking accurate Pi profiling until decided.
